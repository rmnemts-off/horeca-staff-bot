# BarPoint Staff Bot

Telegram-бот для персонала баров и кафе. Заказчик — BarPoint, консалтинг в HoReCa.

Продукт тиражируемый: **один бот обслуживает много заведений**, у каждого свои данные.
Различаются только данные — если для нового заведения потребовалась правка кода, это
считается дефектом (принцип 1.4#4 технического задания).

Главный критерий качества: бармен в разгар смены, одной рукой, за пять секунд получает то,
за чем пришёл.

## Быстрый старт

Нужен Docker с плагином `compose`. Больше ничего ставить не надо — PostgreSQL, Redis
и миграции поднимаются сами.

```bash
cp .env.example .env
```

Заполнить в `.env` три обязательных значения:

- `BOT_TOKEN` — токен от [@BotFather](https://t.me/BotFather);
- `OWNER_TELEGRAM_IDS` — ваш числовой Telegram id (узнать: написать боту
  [@userinfobot](https://t.me/userinfobot));
- `APP_ENV=dev`.

```bash
docker compose up -d
```

Поднимутся пять сервисов: `postgres`, `redis`, одноразовый `migrate` (применяет
`alembic upgrade head` и завершается), `bot` и `scheduler`. Планировщик — **отдельный
процесс**, а не поток внутри бота: критерий приёмки 11.4 требует уметь перезапустить его
независимо и убедиться, что уведомление не потерялось и не задвоилось.

```bash
docker compose logs -f bot          # лог бота
docker compose logs -f scheduler    # лог воркера уведомлений
docker compose restart scheduler    # перезапуск планировщика (критерий 11.4)
docker compose down                 # остановить, данные сохранятся в томах
docker compose down -v              # остановить и стереть базу
```

После `docker compose up` база **пуста**: ни одного рецепта, товара, поставщика или пункта
чек-листа. Это не недоделка, а требование (принцип 1.4#6, критерий приёмки 11.5), и на него
есть тест — [tests/test_empty_delivery.py](tests/test_empty_delivery.py) перечисляет таблицы
из `information_schema` и проверяет, что все они пусты.

## Заведение нового заведения

Ставить ничего не нужно и в базу лезть не нужно: заведение поднимается через интерфейс бота.

1. **Дать первому владельцу право войти.** Добавить его Telegram id в `OWNER_TELEGRAM_IDS`
   (через запятую, если их несколько) и перезапустить: `docker compose up -d bot`.

   Переменная — **одноразовый триггер, а не источник прав** (решение A3). Она открывает
   мастер «Создать заведение» человеку, который пока не состоит нигде; как только заведение
   создано, появляется полноценная строка `venue_members(role='owner')`, и дальше права
   читаются только из базы, как требует раздел 2 ТЗ. Убрать id из переменной после этого
   можно — доступ не пропадёт.

2. **Владелец пишет боту `/start`** и проходит мастер: название, город, таймзона кнопками,
   время смены по умолчанию. Одной транзакцией создаются `venues`, `venue_settings`,
   `venue_members(owner)` и два **пустых** шаблона чек-листа (решение B1).

3. **Владелец заводит сотрудников:** «⚙️ Управление» → «👥 Сотрудники» → «Добавить».
   Указывает ФИО, роль и должность, получает одноразовый код и ссылку вида
   `t.me/<бот>?start=inv_12-A7K9QX4M`. Код живёт 7 дней и срабатывает один раз.

   ФИО задаёт менеджер, а не берётся из профиля Telegram (решение B8): в профилях прозвища,
   а сопоставление при импорте графика идёт по ФИО. Сотрудник видит имя при активации
   и может поправить.

4. **Сотрудник открывает ссылку** (или вводит код текстом) и оказывается в команде.

5. **Владелец заполняет чек-лист открытия:** «⚙️ Управление» → «✅ Чек-листы».
   Сорок пунктов в восьми группах вводятся **одним сообщением**: строка — пункт, строка вида
   `# Барная станция` открывает новую группу, строка с отступа приклеивается к предыдущему
   пункту (решения B6 и B11). Пошагово это час работы с телефона, и ТЗ прямо пишет, что так
   никто делать не станет.

6. **Владелец ставит смены:** «⚙️ Управление» → «📅 График» → «Добавить смену», и отмечает,
   кто открывает. Чек-лист открытия придёт открывающему **сам**, за
   `opening_checklist_lead_minutes` до начала смены (по умолчанию — из настроек заведения).

Второе заведение заводится ровно так же и ничего не знает о первом: почти каждая таблица
несёт `venue_id`, репозитории обязаны по нему фильтровать, а принадлежность объекта заведению
проверяется на сервере при каждом нажатии — чужой `callback_data` не срабатывает
(раздел 3.3 ТЗ, критерий приёмки 11.3).

## Переменные окружения

Полный список с комментариями — в [.env.example](.env.example). Токен и строки подключения
передаются **только через окружение** и ни при каких условиях не попадают в репозиторий
(раздел 9 ТЗ); `.env` в `.gitignore`.

| Переменная | Обязательна | Что это |
|---|---|---|
| `BOT_TOKEN` | да | Токен от @BotFather |
| `APP_ENV` | да | `dev` \| `test` \| `prod`; влияет на проверки при старте |
| `OWNER_TELEGRAM_IDS` | для первого запуска | Telegram id через запятую — одноразовый триггер мастера создания заведения (решение A3) |
| `DATABASE_URL` | вне docker | `postgresql+asyncpg://user:password@host:5432/barpoint` |
| `REDIS_URL` | вне docker | `redis://host:6379/0` — хранилище FSM и кэш |
| `LOG_LEVEL` | нет | `DEBUG` \| `INFO` \| `WARNING` \| `ERROR`, по умолчанию `INFO` |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | только для compose | Учётные данные контейнера базы; из них же собирается `DATABASE_URL` внутри compose |

Внутри `docker compose` `DATABASE_URL` не задаётся: его собирает
[docker/entrypoint.sh](docker/entrypoint.sh) из частей `POSTGRES_*`, чтобы пароль был
записан ровно в одном месте. Заданный снаружи `DATABASE_URL` всегда побеждает — так
передаётся управляемая база и пароль со спецсимволами, которые наивная сборка строки
не закодирует.

**Про `APP_ENV=prod`:** если пароль базы остался равен локальной заглушке `barpoint`,
entrypoint откажется стартовать и скажет почему. Удобство локального стенда не должно
молча доезжать до продакшена.

## Разработка без Docker

Нужны поднятые PostgreSQL 16 и Redis, а строки подключения — в `.env`.

```bash
python -m venv .venv
.venv/bin/pip install -e ".[dev]"
.venv/bin/alembic upgrade head
.venv/bin/python -m src.bot          # бот
.venv/bin/python -m src.scheduler    # воркер уведомлений
```

### Проверки

```bash
.venv/bin/python -m ruff check . && .venv/bin/python -m ruff format --check .
.venv/bin/python -m mypy
.venv/bin/python -m pytest -q
```

`pytest` **обязан быть зелёным без базы**: тесты, которым нужна живая PostgreSQL, помечены
`@pytest.mark.db` и пропускаются, если `DATABASE_URL` недоступен. В CI база есть, и они
выполняются — так что «зелено локально» не заменяет прогон CI.

Отдельно стоит знать про два вида тестов, которые выглядят необычно:

- **сторожа** (`tests/test_no_seed_data.py`, `tests/test_static_repos.py`,
  `tests/bot/test_handler_boundary.py`) разбирают синтаксическое дерево `src/` и падают,
  если в поставку просочились данные, если SQL появился вне репозиториев или если хендлер
  полез в базу мимо сервисов. Каждое правило проверено на коде, который оно обязано ловить;
  модель угроз — случайная ошибка, а не злонамеренный обход, и границы описаны в докстрингах;
- **проводка** (`tests/test_wiring.py`) собирает все репозитории и сервисы из настоящих
  классов, чтобы mypy сравнил их с протоколами. Без неё расхождение контракта не заметит
  никто: структурная типизация проверяется только там, где конкретный класс присваивается
  протоколу.

## Как устроен код

```
src/
├── bot/
│   ├── handlers/      экраны, по модулю на функциональный блок; бизнес-логики нет
│   ├── views/         чистые функции: вью сервиса → текст и клавиатура
│   ├── keyboards/
│   ├── states/        FSM всех сценариев, одним файлом
│   ├── middlewares/   ошибки, лимит, сессия, авторизация, venue-контекст, резолвер callback
│   ├── texts/         ВСЕ пользовательские строки
│   ├── callbacks.py   единая схема callback_data с бюджетом 64 байта
│   └── renderers.py   уведомления → сообщения, для воркера
├── db/
│   ├── models/
│   └── repositories/  доступ к данным; SQL живёт только здесь
├── services/          бизнес-логика, ничего не знающая о Telegram
├── scheduler/         воркер уведомлений, отдельный процесс
└── importers/         разбор Excel (этап 1)
```

Три границы, которые держат эту схему, проверяются тестами, а не договорённостями:

1. **Хендлер не ходит в базу.** Он принимает апдейт, зовёт сервис и рисует ответ. Это нужно,
   чтобы позже поднять веб-админку поверх той же логики (раздел 3.2 ТЗ).
2. **Хендлер не разбирает `callback_data`.** Единый резолвер уже распарсил payload, достал
   объект через репозиторий заведения и проверил права нажавшего (раздел 9 ТЗ).
3. **Ни одной русской строки в `src/` вне `src/bot/texts/`.** Заказчик правит формулировки
   без разработчика (раздел 8.2 ТЗ).

## Что уже работает, а что нет

Этап 0 — «скелет, который живёт»: сквозной путь от создания заведения до пройденного
чек-листа. Подробный отчёт — в [docs/stage0-report.md](docs/stage0-report.md).

**Есть:** онбординг по коду приглашения · главное меню · «Моя смена» и «График» ·
чек-лист открытия, который приходит сам · карточка рецепта с поиском по опечаткам ·
создание заведения, сотрудников, чек-листа, смен и рецептов через интерфейс · журнал
изменений · уведомления менеджеру.

**Нет (этап 1):** импорт Excel и мастер сопоставления колонок · чек-лист закрытия
и проверка наличия · фото в пунктах · списание · заказ поставщику · база знаний · отчёты ·
групповой чат · остальные типы уведомлений раздела 6.

Нереализованные разделы меню **не рисуются вовсе** — ни заглушек, ни «скоро будет»
(решение B7): ТЗ 8.1 запрещает кнопку, ведущую в никуда, а этап 0 меряет ощущение
от рабочего инструмента, и ряд мёртвых кнопок портит именно этот замер.
