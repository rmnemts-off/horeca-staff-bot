# CLAUDE.md — BarPoint Staff Bot

Telegram-бот для персонала баров и кафе. Заказчик — BarPoint, консалтинг в HoReCa.
Продукт тиражируемый: **один бот, много заведений, у каждого свои данные**.

## Шесть продуктовых принципов (ТЗ 1.4, нарушать нельзя)

1. **Всё внутри бота.** Рядовой сотрудник никогда не выходит за пределы Telegram.
   Единственное исключение — ссылка на форму поставщика в сценарии заказа.
2. **Бот приходит сам.** Ключевые действия инициирует бот по расписанию, а не сотрудник
   по своей инициативе.
3. **Это рабочий инструмент, а не обучение.** Никаких курсов, тестов, геймификации.
4. **Один шаблон — много заведений.** Различаются только данные. Если для нового заведения
   потребовалась правка кода — принцип нарушен.
5. **Минимум ввода руками.** Где можно дать выбор кнопками — даём кнопками.
6. **Система поставляется пустой.** Ни одного рецепта, товара, поставщика или пункта
   чек-листа, пока их не завело конкретное заведение.

**Главный критерий качества:** бармен в разгар смены, одной рукой, за 5 секунд получает
то, за чем пришёл. Всё остальное вторично.

## Жёсткие ограничения

- **Никаких данных в поставке.** Ни в миграциях, ни в сид-скриптах, ни константами в коде.
  Единственное исключение — фикстуры внутри `tests/`, которые не выполняются в проде.
  На это есть тест приёмки (ТЗ 11.5): после `docker compose up` и миграций база пуста.
- **Пустое состояние — основной сценарий, а не краевой случай** (ТЗ 8.1). Каждое новое
  заведение начинает с нуля, каждый раздел обязан корректно выглядеть пустым.
- **Бизнес-логика не живёт в хендлерах** (ТЗ 3.2). Хендлер принимает апдейт, вызывает
  сервис, рендерит ответ. Это нужно, чтобы позже поднять веб-админку поверх той же логики.
- **Ни одной русской строки в коде хендлеров.** Все тексты — в `src/bot/texts/`,
  чтобы заказчик правил формулировки без разработчика (ТЗ 8.2).
- **Хранилище — PostgreSQL, не Google Таблицы.** Excel/Sheets — только формат импорта.
- **Не придумывать бизнес-логику, которой нет в ТЗ.** Если ТЗ молчит — вопрос заказчику,
  а не «разумное по умолчанию». В операционке заведения разумное по умолчанию почти всегда
  неверно. Технические решения (библиотеки, паттерны, структура кода) принимаются
  самостоятельно, если не противоречат разделу 3 ТЗ.

## Стек (ТЗ 3.1, решённый вопрос)

Python 3.12 · aiogram 3.x · PostgreSQL 16 · SQLAlchemy 2.0 (async) + Alembic · Redis (FSM и кэш)
· APScheduler · Pydantic v2 / pydantic-settings · openpyxl · pytest + pytest-asyncio
· Docker + docker compose · ruff + mypy

## Структура репозитория

```
src/
├── bot/
│   ├── handlers/      # по модулю на функциональный блок, без бизнес-логики
│   ├── keyboards/
│   ├── states/        # FSM
│   ├── middlewares/   # авторизация, venue-контекст, логирование, rate limit
│   └── texts/         # ВСЕ тексты сообщений
├── db/
│   ├── models/
│   └── repositories/  # доступ к данным, никакого SQL в хендлерах
├── services/          # бизнес-логика, не зависящая от Telegram
├── scheduler/
├── importers/         # разбор Excel
└── config.py
tests/
docs/
```

## Мультитенантность (ТЗ 3.3)

- Почти каждая таблица содержит `venue_id`.
- Middleware на каждом апдейте кладёт `venue_id` в контекст; **репозитории обязаны
  фильтровать по нему**.
- `venue_id = NULL` у `recipes` и `knowledge_articles` — общая библиотека BarPoint.
  Механизм реализуется, но на старте библиотека пуста.
- Права проверяются на сервере на каждом действии, а не скрытием кнопок. Чужой
  `callback_data` не должен срабатывать: проверять принадлежность объекта заведению.

## Часовые пояса (ТЗ 3.4)

У каждого заведения свой `timezone` (IANA). Все расчёты расписания и уведомлений —
в таймзоне заведения, **в БД всё хранится в UTC**.

## Команды

```bash
docker compose up -d          # поднять стенд (postgres, redis, bot), миграции применяются автоматически
docker compose logs -f bot    # логи бота
alembic upgrade head          # миграции вручную
pytest                        # тесты
ruff check . && ruff format --check .
mypy src
```

Локально без docker: `.venv/bin/python -m src.bot` при поднятых postgres и redis.

## Переменные окружения

Токен бота и строки подключения — **только через переменные окружения**, ни при каких
условиях не в репозитории (ТЗ 9). Актуальный список — в `.env.example`.
Файл `.env` в `.gitignore` и в репозиторий не попадает.

## Дисциплина работы (ТЗ 12)

- Коммиты небольшие, по одному логическому изменению.
- Каждый функциональный блок закрывается тестом до перехода к следующему.
- Общий контракт — модели и интерфейсы репозиториев; фиксируются первыми, дальше
  направления идут параллельно. Агенты не редактируют одни и те же файлы одновременно.
- Тексты сообщений — сразу в `texts/`, даже черновые.
- После каждого этапа — короткий отчёт: что сделано, что осталось, какие решения
  пришлось принять самостоятельно.

## Про референсную таблицу

`tests/fixtures/reference/Invasion.xlsx` — реальная рабочая таблица бара Invasion Universe,
16 листов. Нужна ровно для двух вещей: понять, как работа устроена в жизни, и служить
эталоном при написании и тестировании парсеров.

**Её содержимое в продукт не переносится.** Ни рецептуры, ни напитки, ни ингредиенты,
ни поставщики, ни номенклатура, ни пункты чек-листов. Допустимо только залить фрагмент
во временное окружение, проверить UX на реальном объёме и удалить.

Пустая поставка и наличие импорта не противоречат друг другу: перенос данных — обязательная
функция первой версии (ТЗ 7), заведение загружает свои файлы само через мастер сопоставления
колонок. Пустой поставляется система, а не рабочее заведение.
