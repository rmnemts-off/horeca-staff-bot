### Имена ENUM-типов: префикс `bp_`

Все десять типов названы `bp_unit`, `bp_member_role`, `bp_order_status` и так далее.
Без префикса схема занимает в `public` имена, которые в чужой базе заняты с высокой
вероятностью (`unit`, `order_status`, `member_role`, `run_status`), а продукт по **ТЗ 1.4#4**
тиражируемый и не обязан быть единственным в своей базе. Префикс относится только к имени
типа: значения внутри — дословно из раздела 4 ТЗ.

Вторая половина той же проблемы — `CREATE TYPE` не имеет формы `IF NOT EXISTS`. Миграция
создаёт типы в идемпотентной обёртке
(`DO $$ BEGIN CREATE TYPE ...; EXCEPTION WHEN duplicate_object THEN NULL; END $$`), поэтому
`upgrade head`, упавший на середине, можно повторить: это симметрично `DROP TYPE IF EXISTS`
в `downgrade()`.

## 2. Уточнения, которые не меняют состав полей

ТЗ 4: «Названия полей можно уточнять, состав — нет». Ниже — уточнения nullability и типов.

- **NULL там, где ТЗ не ставит пометку, но сценарий допускает отсутствие значения:**
  `users.phone`, `users.username`, `users.last_seen_at` (телефон никогда не спрашивается в
  сценариях этапа 0, username в Telegram может отсутствовать); `venue_members.position` и
  `invite_codes.position` (**ТЗ 4.1** допускает выдачу кода без должности);
  `products.category_id` (**ТЗ 8.1**: позиция может быть заведена до категорий);
  `orders.supplier_id` (**ТЗ 5.7**: у каналов `marketplace` / `market` / `household`
  поставщика нет); `checklist_runs.shift_id` (**ТЗ 5.4**: `stock` привязан к настройке
  заведения, а не к смене); `notifications.user_id` (**ТЗ 6**: сообщение в рабочую группу).
- **Все поля `*_by`** (`created_by`, `updated_by`, `completed_by`, `used_by`, `cancelled_by`) —
  nullable с `ON DELETE SET NULL`: запись переживает деактивацию пользователя
  (**ТЗ 5.1**: «деактивация сотрудника не удаляет его историю»). Ключевые ссылки на автора
  (`shifts.user_id`, `checklist_runs.user_id`, `orders.user_id`, `writeoffs.user_id`) стоят
  `RESTRICT`, поэтому строку `users` вообще нельзя удалить, пока за ней числится история —
  см. следующий раздел.
- **`recipe_ingredients.qty` и `unit` — оба nullable** (**D4**): в жизни встречаются и
  количество без единицы, и единица внутри текста.
- Все `timestamptz` — UTC, все `TIME` — локальное время заведения (**ТЗ 3.4**, **D12**);
  проверяется тестом `test_all_timestamps_are_timezone_aware`.
- PK — `BIGINT GENERATED BY DEFAULT AS IDENTITY` (**D14**), не UUID: два UUID в
  `callback_data` не помещаются в 64 байта.
- **Минимальная версия PostgreSQL — 15** (`docker-compose.yml` пинит 16). Требуют её
  `NULLS NOT DISTINCT` в `uq_recipes_venue_category_name` и форма `ON DELETE SET NULL (колонка)`
  в составных внешних ключах, см. ниже. Требование не на словах: первая инструкция миграции
  `0001` проверяет `server_version_num` и падает с внятным сообщением, а не с синтаксической
  ошибкой на середине.

### Ссылочные действия: что переживает удаление

Правило: **строка-история не удаляется вслед за строкой-справочником**. Отсюда разбиение
ниже; полный перечень внешних ключей — в `alembic/versions/0001_initial.py`.

| Внешний ключ | Действие | Почему |
|---|---|---|
| `shifts.user_id`, `checklist_runs.user_id`, `orders.user_id`, `writeoffs.user_id` | `RESTRICT` | **ТЗ 5.1**: «деактивация сотрудника не удаляет его историю». Строку `users` физически удалить нельзя, пока за человеком числится хоть одна смена, run, заказ или списание. Продуктового сценария удаления пользователя в ТЗ нет — есть деактивация (`users.is_active`, `venue_members.is_active`) |
| `checklist_runs.shift_id`, `writeoffs.shift_id` | `SET NULL (shift_id)` | Удаление смены — штатная операция (план, задачи **29** и **33**). Каскад снёс бы `checklist_runs` и через него все отметки `checklist_run_items`, то есть менеджер, убирая старую смену, молча стирал бы пройденный чек-лист — прямое нарушение **ТЗ 4.3** («отчёт за прошлый месяц не должен поехать») и **ТЗ 5.9**. Колонка nullable по другой причине (`stock`-чек-лист не привязан к смене), поэтому partial-индекс `uq_checklist_runs_shift_type ... WHERE shift_id IS NOT NULL` это переживает |
| `checklist_runs.template_id`, `writeoffs.product_id`, `writeoffs.reason_id`, `order_items.product_id`, `checklist_run_items.item_id` | `RESTRICT` | Справочник, на который ссылается история, не удаляется молча; менеджер деактивирует запись (`is_active`) |
| `*.venue_id`, `checklist_items.template_id`, `checklist_run_items.run_id`, `*_ingredients.*_id`, `supplier_products.*`, `order_items.order_id` | `CASCADE` | Дочерние строки не существуют без родителя; удаление заведения уносит его данные целиком |
| `venue_members.user_id`, `notifications.user_id` | `CASCADE` | Это не история, а членство и очередь: без пользователя они бессмысленны. На практике недостижимо — удалить строку `users` не даст `RESTRICT` из первой строки таблицы |
| Все `*_by`, `users.active_venue_id`, `products.category_id`, `products.default_supplier_id`, `orders.supplier_id`, `product_categories.parent_id`, `recipe_ingredients.product_id`/`prep_id`, `prep_ingredients.product_id` | `SET NULL` | Ссылка вспомогательная: запись остаётся осмысленной без неё |

### Целостность поперёк заведений — составные внешние ключи

`venue_id` в дочерней строке не спасает от ссылки на объект **чужого** заведения:
`checklist_runs(venue_id=A, template_id=<шаблон B>)` на уровне БД до сих пор был законной
строкой. Аргумент D9 сюда не распространяется — это не дочерняя строка, а ссылка между
двумя venue-скоупными таблицами. Закрыто составными ключами: на родителе появляется
`UNIQUE (venue_id, id)`, на ребёнке — `FOREIGN KEY (venue_id, <fk>) REFERENCES parent (venue_id, id)`.

| Ссылка | Ограничение |
|---|---|
| `checklist_runs` → `checklist_templates` | `fk_checklist_runs_venue_template` |
| `checklist_runs` → `shifts` | `fk_checklist_runs_venue_shift` |
| `writeoffs` → `products` / `writeoff_reasons` / `shifts` | `fk_writeoffs_venue_product` / `_venue_reason` / `_venue_shift` |
| `orders` → `suppliers` | `fk_orders_venue_supplier` |
| `products` → `product_categories` / `suppliers` | `fk_products_venue_category` / `_venue_default_supplier` |
| `product_categories` → `product_categories` (родительская категория) | `fk_product_categories_venue_parent` |

Новые `UNIQUE (venue_id, id)`: `checklist_templates`, `shifts`, `products`,
`product_categories`, `suppliers`, `writeoff_reasons`.

Две детали реализации:

- где действие было `SET NULL`, используется форма **PostgreSQL 15+** `ON DELETE SET NULL (колонка)`.
  Обычный `SET NULL` обнулил бы весь ключ, включая `venue_id`, а он `NOT NULL`;
- в ORM `ChecklistRun.template` и `ChecklistRun.shift` объявлены `viewonly=True`. Обе связи
  теперь включают `venue_id` в условие соединения, и запись идёт только через колонки-идентификаторы,
  которые проставляет репозиторий. Побочный эффект приятный: `run.template` физически не может
  подтянуть шаблон чужого заведения.

**Что осталось на сервисном слое** и почему не закрыто в БД:

- `order_items(order_id, product_id)` и `checklist_run_items(run_id, item_id)` — обе таблицы
  дочерние и своего `venue_id` не имеют, а составной ключ требует колонки, по которой сверяться.
  Завести её значило бы денормализовать `venue_id` в дочернюю строку и нарушить **D9** (второй
  источник истины). Проверку делает сервис: состав заказа собирается из номенклатуры своего
  заведения, `checklist_run_items` — из пунктов шаблона своего run;
- `notifications.entity` / `entity_id` — полиморфная ссылка, внешним ключом не выражается.

### Поиск по `aliases`

**ТЗ 4.6**: «поиск по `name`, `aliases` и полнотекстово, с устойчивостью к опечаткам».
Раньше индексом были покрыты только `recipes.name` и `knowledge_articles.title`, то есть
ровно половина требования. Добавлены два GIN-индекса по массиву синонимов с **классом
операторов по умолчанию** (`array_ops`): они обслуживают точное попадание в синоним —
`aliases && ARRAY[:q]` и `:q = ANY(aliases)`.

Триграммный индекс поверх массива сознательно **не** заводится: для него нужно выражение
вида `array_to_string(aliases, ' ')`, а эта функция в PostgreSQL помечена `STABLE`, и
индексировать её без собственной `IMMUTABLE`-обёртки нельзя. Заводить функцию в базе ради
этапа 0 несоразмерно: при ориентире **ТЗ 5.5** (~200 позиций) similarity-проход по `aliases`
идёт сканированием и укладывается в правило «5 секунд» с большим запасом. Если объём
вырастет — обёртка + GIN `gin_trgm_ops` по выражению добавляются отдельной миграцией,
ломающих изменений это не требует.

### Уникальность `dedup_key`

Ключ обязателен (`NOT NULL`), но уникален **только среди живых строк очереди**:
`WHERE status IN ('scheduled','sending')`. Глобальный UNIQUE, каким он был сначала, ломает
два обычных сценария:

1. **Задача 33** — открывающего сняли со смены, уведомление ушло в `cancelled`; назначили
   обратно — вставка с тем же ключом упирается в конфликт, хотя логически строка новая.
2. **Задача 19** — событийное уведомление («рецепта нет») по тому же объекту второй раз
   не вставится, и планировщику пришлось бы выдумывать искусственно уникальные ключи для
   немедленных уведомлений.

Отправленная, отменённая и провалившаяся строка — это история; ключ она не держит.
Частичный индекс и есть цель `ON CONFLICT` в `upsert_scheduled` (**задача 14**):
`ON CONFLICT (dedup_key) WHERE status IN ('scheduled','sending') DO UPDATE ...`. Список
статусов зафиксирован константой `ACTIVE_NOTIFICATION_STATUSES` в `src/db/models/service.py`,
чтобы индекс и запрос не разъехались.

### Чем на самом деле гарантируются критерии 11.3 и 11.5

Два статических сторожа — `tests/test_static_repos.py` (изоляция заведений) и
`tests/test_no_seed_data.py` (пустая поставка) — читают исходники и потому срабатывают
всегда, в том числе на машине без PostgreSQL. Важно понимать, чего их зелёный цвет **не**
означает.

**Модель угроз — случайная ошибка разработчика или агента, а не злоумышленник.** Они ловят
перепутанный оператор (`!=` вместо `==`), фильтр, «расширенный» через `or_(..., true())`,
`session.get()` вместо `by_id()`, справочник, положенный в JSON рядом с моделями, дефолт
с текстом в колонке, кортеж ORM-объектов на уровне модуля, сервис в compose с
`entrypoint:` на сид-скрипт. Тест и проверяемый код лежат в одном репозитории: кто правит
одно, правит и другое, — поэтому **намеренный** обход не закрывается сознательно, чтобы не
платить ложными срабатываниями за гонку, которую защита не выигрывает. Открытыми оставлены,
в частности: расщепление ключевого слова между литералами (`"INSER" "T INTO"`), base64 и
`chr()`, сборка строки в рантайме, сессия под нестандартным именем, реэкспорт конструктора
SQL через свой модуль, доступ по цепочке отношений от глобальной таблицы, формулировки в
`texts/`, разложенные по отдельным именованным константам или атрибутам класса, и контент,
записанный идентификаторами (`["bar_top", "ice_bin"]`).

**Настоящая гарантия даётся на живой базе.**

| Критерий | Чем закрывается по-настоящему | Чем страхуется |
|---|---|---|
| **11.5** — после миграций база пуста | `tests/test_empty_delivery.py`: свежая БД, `alembic upgrade head` и ничего больше; список таблиц берётся из `information_schema`, а не захардкожен; в каждой ноль строк. Помечен `db`, в CI обязан реально выполниться, а не пропуститься | `tests/test_no_seed_data.py` |
| **11.3** — изоляция заведений | Тест приёмки **36** (план, задачи 11–13, 28) на живой БД: A не читает данные B, чужой `callback_data` отклоняется сервером, дочерняя строка недостижима поперёк заведений. Ниже — уровень схемы: join в `ChildRepository` и составные внешние ключи `(venue_id, id)` | `tests/test_static_repos.py` плюс проверка `venue_column` в рантайме (`SEALED_SCOPE_ATTRIBUTES`, `_checked_venue_column` в `src/db/repositories/base.py`) |

Статика — дешёвый сторож, который работает везде и всегда: он ловит ошибку до того, как она
доедет до живого теста, и прикрывает код, который живыми тестами ещё не покрыт. Полным
доказательством он не является ни для одного из двух критериев.

## 4. Открытые вопросы (в схему не попали)

- **Q1. `product_kind` и «Заготовки» как верхний раздел.** ТЗ 4.4 задаёт четыре значения:
  `alcohol`, `non_alcohol`, `ingredient`, `other`. ТЗ 5.6 в сценарии называет три раздела
  (Алкоголь / Безалкоголь / Ингредиенты), а в правилах — четыре: «алкоголь, безалкоголь,
  ингредиенты, **заготовки**». Оставлен состав раздела 4. Если заказчик подтвердит списание
  заготовок, значение добавляется `ALTER TYPE ... ADD VALUE` — операция не ломающая.
- **Q2. `stock`-чек-лист.** ТЗ 5.4 обещает «список недостающего», а из булевых галочек он не
  собирается: нужны связь пункта с номенклатурой и состояние вместо галочки. Отложено (**C5**).
- **Q3. Переиспользуемая схема сопоставления колонок.** ТЗ 7 п.7 требует привязки схемы к
  паре (заведение, тип данных). Сейчас схема хранится в `import_jobs.mapping`, то есть на одно
  задание. Отдельная таблица заводится на этапе 1 вместе с импортом — тогда же станет ясно,
  нужна ли история схем.
- **Q4. «Переоткрыть» run.** ТЗ 5.4 разрешает менеджеру переоткрыть чек-лист, но не требует
  отчёта по переоткрытиям. Факт пишется в `audit_log`; отдельные поля не заводим.
- **Q5. Замена смены.** ТЗ 5.3 описывает переназначение смены на другого сотрудника
  (`shifts.user_id` меняется, уведомления переезжают по `shift_id`). Истории замен ТЗ не просит.
- **Q6. Правка записи из общей библиотеки** (`venue_id IS NULL`) — **C4**, отложено; поэтому
  `preps` не входит в белый список `library()` в репозиториях (**D9**), хотя `venue_id` там
  nullable по ТЗ 4.6.
