# Решения этапа 0

Зафиксировано до начала кодирования. Основание: ТЗ 12 «Перед началом».

---

## Ответы заказчика (группа A)

### A1. Тестовый контур — два аккаунта

| Кто | Telegram | `telegram_id` | Роль в БД |
|---|---|---|---|
| Управляющий | `@xawad1` | `1672818749` | `owner` |
| Бармен | `@rmnemts_off` | `917323199` | `staff` |

Управляющий заведён как `owner`, а не `manager`, потому что кто-то должен создать заведение
при пустой базе, а по ТЗ 2 `owner` включает все права `manager`. Сценарий барменеджера
на этапе 0 проверяется под этой ролью; отдельный `manager` появится на этапе 2.

### A2. Тестовое заведение

| Параметр | Значение |
|---|---|
| Название | PIMS |
| Город | Москва |
| Таймзона | `Europe/Moscow` |
| Стандартная смена | 08:00–23:00 (15 часов) |

### A3. Первый владелец

`OWNER_TELEGRAM_IDS` в `.env` — одноразовый триггер. При `/start` от такого id бот создаёт
запись `users` и показывает мастер «Создать заведение»; по завершении мастера появляется
полноценная строка `venue_members(role='owner')`. **После этого права читаются только из БД**,
как требует ТЗ 2. Переменная окружения — конфигурация, а не контент: критерий 11.5 (пустая
база после миграций) не нарушается.

### A4. Получатель уведомлений «менеджеру»

Все активные `venue_members` заведения с ролью `manager`. Если менеджеров в заведении нет —
`owner`. Реализуется одной функцией-резолвером в `src/services/access.py`, чтобы правило
не разъехалось по пяти файлам.

## Решения, принятые на своё усмотрение (группа B, делегировано заказчиком)

### B1. Дефолтный шаблон чек-листа — пустой

При создании заведения создаются шаблоны `opening` и `closing` с `version=1`, `is_active=true`
и **нулём пунктов**. Формулировка ТЗ 5.4 «на старте заводится дефолтный шаблон» читается как
«в момент создания заведения», а не «в поставке». Иначе прямой конфликт с принципом 1.4#6
и критерием 11.5. Правило 8.1 «чек-лист без пунктов не отправляется» уже предполагает
существование пустого шаблона.

### B2. Просрочка — буквально по ТЗ

`начало смены + checklist_overdue_minutes`, как написано в 5.4 и в разделе 6. Для чек-листа
открытия — единственного на этапе 0 — формула корректна.

Для чек-листа закрытия она сломается: он уходит за 30 минут до **конца** смены и будет помечен
просроченным за много часов до собственной отправки. Не переписываем формулу впрок: на этапе 1
якорь станет полем типа чек-листа (`начало смены` для `opening`, `момент отправки` для
`closing`/`stock`). Помечено в задачах этапа 1.

### B3. Версионирование шаблона — copy-on-write

Пока на шаблон не ссылается ни один `checklist_run`, правки идут на месте. После первой ссылки
правка создаёт новую версию, старые `runs` продолжают ссылаться на прежнюю.

Буквальная трактовка ТЗ 4.3 («правка создаёт новую версию») породила бы 40 версий шаблона при
заведении чек-листа на 40 пунктов. Требование «отчёт за прошлый месяц не поедет» выполняется
полностью.

### B4. Смена без открывающего — сохраняется с предупреждением

Смена сохраняется, и на том же экране бот пишет, что открывающий не назначен и чек-лист
открытия не придёт. **Отдельного типа уведомления не заводим** — раздел 6 ТЗ содержит закрытый
перечень из восьми типов, и такого в нём нет. Это текст экрана, а не пуш.

Инвариант «не более одного `is_opener` и одного `is_closer` на дату» проверяется в сервисном
слое, а не жёстким индексом: жёсткий индекс не даст пройти транзакции сценария замены смены
на этапе 1.

### B5. Создание рецепта через интерфейс — входит в этап 0

Минимальная форма: название, категория, посуда, метод, лёд, состав строками, гарниш,
приготовление. Без неё раздел рецептов на тестовом заведении пуст навсегда, сценарий 5.5
в ручном прогоне не проверить и критерий 11.1 в этой части не закрыть.

### B6. Массовый ввод пунктов чек-листа — входит в этап 0

Менеджер присылает одно сообщение: каждая строка — пункт, строка вида `# Название` открывает
новую группу. Это не импорт (парсера нет, данных в поставке нет), а обычный текстовый ввод.
Реальный чек-лист — 8 групп и около 40 пунктов; через пошаговый сценарий это час работы
с телефона, ТЗ 7 само пишет, что так никто делать не станет.

### B7. Главное меню — нереализованные пункты скрыты

На этапе 0 у `staff` три кнопки: «📋 Моя смена», «📅 График», «📖 ТТК и рецепты». Списание,
Заказ и База знаний не рендерятся вовсе. ТЗ 8.1 запрещает битые кнопки; этап 0 меряет ощущение
от рабочего инструмента, и заглушки «скоро будет» портят именно этот замер. Меню собирается
из реестра с флагом доступности — на этапе 1 пункты включаются флагом, код клавиатуры
не трогается.

### B8. ФИО задаёт менеджер при выдаче кода

Сотрудник видит его при активации и может поправить; менеджер может переименовать позже.
Имя из профиля Telegram не используем — там прозвища, а сопоставление при импорте графика
(ТЗ 5.3) идёт по ФИО. Требует поля `invite_codes.full_name`, которого нет в ТЗ 4.1.

## Отложено до этапа 1

- **C4. Правка записи из общей библиотеки BarPoint** (`venue_id IS NULL`). ТЗ 3.3 описывает
  только чтение. На этапе 0 библиотека пуста, сценарий недостижим — решаем, когда появится.
- **C5. Чек-лист наличия по зонам.** Из булевых галочек нельзя собрать «список недостающего»,
  который обещает ТЗ 5.4. Понадобится связь пункта с номенклатурой и состояние вместо галочки
  (в наличии / мало / нет). Схема закладывается сейчас так, чтобы это добавлялось без
  переделки: тип `stock` уже в enum.
- **C1–C3** (месяц в файле графика, обезличенные сотрудники, совпадающие названия рецептов) —
  вопросы импорта, актуальны с этапа 1.
