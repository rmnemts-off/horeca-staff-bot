# Отчёт этапа 0 — BarPoint Staff Bot

Основание: ТЗ 12 («после каждого этапа — короткий отчёт»), критерии приёмки раздела 11.

Этап 0 по ТЗ 10.1 — «скелет, который живёт»: сквозной путь от создания заведения до
пройденного чек-листа, который приходит сам. Не витрина, а рабочий инструмент в минимальном
объёме.

| | |
|---|---|
| Коммитов в `main` | 53 |
| Модулей в `src/` | 102 (25 500 строк) |
| Тестов | **3006 зелёных, 69 пропускаются без БД** (31 200 строк) |
| `ruff`, `ruff format`, `mypy` | чисто, `mypy` strict на `src/services` и `src/db` |
| CI | зелёный на каждом пуше, с живыми PostgreSQL 16 и Redis |

## Что работает

**Вход.** `/start`, диплинк `?start=inv_XXXX`, код текстом. Менеджер выдаёт одноразовый код
на 7 дней с ролью, должностью и ФИО; сотрудник подтверждает имя или правит его. Человек,
работающий в двух заведениях, выбирает одно, и выбор переживает перезапуск. Незнакомец
получает предложение кода — и **ничего больше**: ни подсказки, ни списка возможностей.

**Главное меню.** Постоянная реплай-клавиатура. У сотрудника три раздела, у управляющего
четвёртый. Нереализованные разделы не рисуются вовсе (решение B7). Нажатие пункта меню
прерывает незаконченный сценарий, спрашивая только если было что терять.

**«Моя смена».** Текущая смена по окну времени, и только при её отсутствии — ближайшая
будущая. При смене 14:00–00:00 в 00:30 сотрудник видит ту, в которой стоит, а не завтрашнюю.
Состав смены, пометки открытия и закрытия, вход в уже отправленный чек-лист.

**«График».** Свои смены на две недели.

**Чек-лист открытия.** Приходит **сам** за `opening_checklist_lead_minutes` до смены. Одно
сообщение: заголовки групп, строки `[ ]`/`[✓]`, счётчик; кнопками — компактные маркеры
пунктов текущей группы (решение D11). Повторный вход редактирует то же сообщение. Завершение
с пропусками спрашивает причину и уведомляет управляющего, критичные пункты первыми.

**Рецепты.** Поиск с опечатками (`мохита` → `Мохито`), по алиасам, регистронезависимо; список
до 10 с пагинацией, категория в подписи кнопки. Карточка не рисует пустых полей. «Сообщить,
что рецепта нет» уведомляет управляющего.

**Управление.** Создание заведения мастером (название, город, таймзона кнопками, окно смены).
Сотрудники: список, выдача кода со ссылкой, деактивация без удаления истории. Чек-листы:
редактор с массовым вводом — 40 пунктов в 8 группах одним сообщением. График: создание смены,
назначение открывающего и закрывающего, удаление. Настройки заведения. Рецептуры: форма
добавления карты.

**Планировщик.** Отдельный процесс. Обходит заведения, забирает пачку через
`FOR UPDATE SKIP LOCKED`, доставляет, реанимирует зависшие строки. Блокировка бота, лимит
Telegram и неизвестный тип уведомления не роняют пачку.

**Журнал изменений.** Каждое изменение конфигурации заведения пишется в `audit_log`
с автором и диффом (границы — решение B13).

### Чего я не сделал и почему

**Ручной прогон приёмки (задача 47) не выполнен.** Для него нужны две вещи, которых нет:

1. **Docker** на машине сборки — а с ним PostgreSQL и Redis. Без них бот физически не
   поднять: 69 тестов, которым нужна живая база, локально пропускаются и выполняются только
   в CI. Установку системного софта я делать не стал: это выходит за рамки задачи и меняет
   машину заказчика.
2. **Второй живой человек.** Сценарий 11.1 по определению двусторонний: управляющий выдаёт
   код, **сотрудник его активирует**, управляющий видит его в списке и ставит на смену.
   Обе стороны — реальные Telegram-аккаунты, и нажать за них кнопки нельзя.

Запускать бота с боевым токеном в одиночку я тоже не стал: бот начал бы принимать апдейты
и отвечать реальным людям, а это действие наружу, которого никто не просил.

**Что вместо этого.** Всё, что можно проверить без живого стенда, проверено: сценарии
прогоняются через фейкового `Bot` с настоящим деревом роутеров и настоящим резолвером,
очередь уведомлений — на настоящей PostgreSQL в CI. Инструкция для прогона — в
[README](../README.md), раздел «Заведение нового заведения»; порядок шагов там же и есть
порядок критерия 11.1.

**Замеры производительности (задача 44, вторая половина)** не сняты по той же причине:
скрипт `tests/tools/load_reference_fragment.py --measure` считает медиану и p95 против
бюджета ТЗ 9, но ему нужна база с залитым фрагментом.

## Решения, принятые самостоятельно

Полный список — в [decisions-stage0.md](decisions-stage0.md). Заказчик ответил на вопросы
группы A и делегировал остальное; ниже те решения, которые заметнее всего влияют на продукт.

| | Решение | Почему так |
|---|---|---|
| B1 | Шаблоны чек-листов создаются **пустыми** вместе с заведением | «На старте заводится дефолтный шаблон» из ТЗ 5.4 прочитано как «в момент создания заведения», а не «в поставке» — иначе прямой конфликт с принципом 1.4#6 и критерием 11.5 |
| B3 | Версионирование шаблона — copy-on-write | Буквальная трактовка ТЗ 4.3 дала бы 40 версий на чек-лист из 40 пунктов. Требование «отчёт за прошлый месяц не поедет» выполняется полностью |
| B4 | Смена без открывающего сохраняется с предупреждением на экране | Раздел 6 ТЗ содержит закрытый перечень из восьми типов уведомлений, и такого в нём нет. Это текст экрана, а не пуш |
| B6 | Массовый ввод пунктов одним сообщением | Реальный чек-лист — 8 групп и 40 пунктов; пошагово это час с телефона, и ТЗ 7 само пишет, что так никто делать не станет |
| B7 | Нереализованные пункты меню скрыты, а не заглушены | ТЗ 8.1 запрещает битые кнопки; этап 0 меряет ощущение от рабочего инструмента, и ряд мёртвых кнопок портит именно этот замер |
| B10 | Горизонт «ближайшей смены» снят совсем | В коде стояла константа в 31 день — придуманное бизнес-правило, которого в ТЗ нет |
| B13 | Отметки чек-листа в `audit_log` **не** пишутся | 40 записей за одно открытие смены — не журнал изменений, а вторая копия `checklist_run_items` |

## Что осталось на этап 1

Из объёма ТЗ: импорт Excel и мастер сопоставления колонок · чек-лист закрытия и проверка
наличия · фото в пунктах · эскалация критичных пунктов · списание · заказ поставщику · база
знаний · отчёты · групповой чат `/bind` · inline-режим · заготовки отдельным разделом ·
замена смены с переездом уведомлений · «График всей команды» · переключение активного
заведения · остальные пять типов уведомлений раздела 6.

Найдено по ходу и записано как долг:

- **Формула просрочки** (решение B2) верна для чек-листа открытия и сломается для закрытия:
  он уходит за 30 минут до **конца** смены и будет помечен просроченным за часы до отправки.
  На этапе 1 якорь становится полем типа чек-листа.
- **Правка записи из общей библиотеки BarPoint** (C4): ТЗ 3.3 описывает только чтение.
  На этапе 0 библиотека пуста, сценарий недостижим.
- **Чек-лист наличия по зонам** (C5): из булевых галочек нельзя собрать «список
  недостающего», который обещает ТЗ 5.4. Понадобится связь пункта с номенклатурой и
  состояние вместо галочки. Схема заложена так, чтобы это добавилось без переделки.
- **Редактирование существующей смены** и замена сотрудника на ней: карточка смены сейчас
  меняет только пометки и удаляет.
- **Чтение графика всего заведения одним запросом**: экран управляющего собирает две недели
  повторными вызовами `roster(date)`.

## Как это проверять

```bash
docker compose up -d
docker compose logs -f bot
```

Порядок ручного прогона — [README](../README.md), «Заведение нового заведения». Он же
является сценарием критерия 11.1: создать заведение → выдать код → сотрудник активирует →
менеджер видит его в списке и ставит на смену открывающим → завести чек-лист → дождаться,
что чек-лист **придёт сам** → пройти его → найти рецепт.

Быстрее всего проверить «бот приходит сам», не дожидаясь утра: поставить смену на ближайшее
время и уменьшить `opening_checklist_lead_minutes` в настройках заведения. Если расчётный
момент уже прошёл, а смена ещё не началась, уведомление ставится в очередь немедленно.
