# Стартовый промпт для Claude Code

Вставить первым сообщением в пустом репозитории. Рядом положить два файла:
`TZ-barpoint-staff-bot.md` и `tests/fixtures/reference/Invasion.xlsx`.

---

Ты разрабатываешь Telegram-бота для персонала баров и кафе. Заказчик — BarPoint, консалтинговая компания в HoReCa. Продукт тиражируемый: один бот, много заведений, у каждого свои данные.

**Читай в этом порядке:**

1. `TZ-barpoint-staff-bot.md` — полное техническое задание. Прочитай целиком, не по диагонали. Раздел 0 объясняет, как с ним работать.
2. `tests/fixtures/reference/Invasion.xlsx` — **референс, а не данные проекта.** Это реальная рабочая таблица одного бара: 16 листов, по которым команда живёт сегодня. Она нужна ровно для двух вещей: понять, как эта работа устроена в жизни (какие сущности, поля, объёмы, форматы), и служить эталоном при написании и тестировании парсеров. Открой её через openpyxl и посмотри структуру глазами — в ТЗ, раздел 7, описано, как оно устроено, но детали формата видны только в файле.
   Онлайн-версия (доступ на просмотр): https://docs.google.com/spreadsheets/d/12EYsYelgNryWmo6O6uORXQysxJOe1lloIpL9tomgCKM/edit

**Критическое требование: система поставляется пустой.**

Ни рецептуры, ни напитки, ни ингредиенты, ни поставщики, ни номенклатура, ни пункты чек-листов из референсной таблицы в продукт не попадают. Ничего из неё не оказывается в миграциях, сид-скриптах, константах или фикстурах продового окружения. После `docker compose up` и миграций база пуста, и на это есть тест.

Единственное допустимое использование содержимого таблицы — залить фрагмент во временное окружение, чтобы проверить работоспособность и удобство интерфейса на реальном объёме (чек-лист из сорока пунктов, две сотни рецептов), посмотреть и удалить.

Прямое следствие: **пустое состояние — основной сценарий, а не краевой случай.** Каждое новое заведение начинает с нуля, и каждый раздел бота должен корректно выглядеть и вести себя пустым. Это раздел 8.1 ТЗ.

**Не путай пустую поставку с отсутствием импорта.** Перенос данных — обязательная функция первой версии, раздел 7 ТЗ: заведение присылает свои файлы и загружает их само, через мастер сопоставления колонок. Пустой поставляется система, а не рабочее заведение. Именно поэтому парсеры должны быть устойчивыми: структура файла у каждой точки своя, и референсная таблица — лишь один из вариантов того, как это выглядит.

**Что делаем в этой сессии — этап 0 из раздела 10.1 ТЗ:** тестовый бот на двух пользователей (барменеджер и сотрудник). Онбординг, главное меню, ручное создание смены, чек-лист открытия, карточка рецепта. Тестовое заведение создаётся с нуля через интерфейс — это заодно проверка, что заведение реально поднимается руками.

**Порядок работы:**

1. Прочитай ТЗ и референсную таблицу.
2. Задай вопросы из раздела 13, помеченные `[!]`, плюс всё, что осталось неясным после чтения. Не начинай кодить, пока нет ответов на блокирующие.
3. Создай `CLAUDE.md`: стек, структура, конвенции, команды запуска и тестов, шесть продуктовых принципов из раздела 1.4.
4. Покажи план этапа 0 задачами. Дождись подтверждения.
5. Реализуй. Направления из раздела 12 можно вести параллельными агентами, но сначала зафиксируй модели и интерфейсы репозиториев — это общий контракт, и агенты не должны править одни и те же файлы.

**Чего делать нельзя:**

- Класть любые данные в поставку. См. выше — это главное ограничение проекта.
- Придумывать бизнес-логику, которой нет в ТЗ. Если ТЗ молчит — спроси. В операционке заведения «разумное по умолчанию» почти всегда неверно.
- Проектировать под пять демонстрационных записей. Ориентиры реальные: около 200 позиций техкарт, чек-лист открытия на 40 пунктов в восьми группах, десяток поставщиков. Интерфейс и поиск должны это выдерживать.
- Складывать бизнес-логику в хендлеры aiogram. Логика — в сервисах, хендлер только принимает апдейт и рендерит ответ.
- Хранить данные в Google Таблицах. Хранилище — PostgreSQL.
- Уводить рядового сотрудника из Telegram куда-либо. Единственное исключение — ссылка на форму поставщика в сценарии заказа.

**Главный критерий качества:** бармен в разгар смены, одной рукой, за 5 секунд получает то, за чем пришёл. Всё остальное вторично.
