# Часть I. Доступы: аварийные исправления

## 1.1 Что произошло

Заказчик, будучи владельцем заведения, выпустил пригласительную ссылку с ролью
«управляющий» и перешёл по ней со своего же аккаунта. Результат: роль сменилась на
`manager`, имя в системе сменилось на имя с кода, часть разделов исчезла. Затем он нажал
«Отключить» на собственной карточке и потерял доступ полностью. Восстановиться удалось
только потому, что часом ранее он выпустил и не активировал ещё один код — с ролью
владельца. **Если бы этого кода не было, заведение осталось бы без владельца необратимо,
и починка потребовала бы ручного `UPDATE` в базе.**

Журнал заведения PIMS подтверждает последовательность: активация manager-кода в 10:27:15,
самодеактивация в 10:28:02, спасение owner-кодом в 10:42:21.

## 1.2 Подтверждённые дефекты

| № | Дефект | Где | Последствие |
|---|---|---|---|

| Д-4 | `MemberService.set_role` не подключён ни к одному экрану | [members.py:180](../src/services/members.py) | Единственный способ сменить роль — код приглашения, то есть ровно сломанный путь |
| Д-5 | Управляющий может деактивировать владельца | [members.py:170](../src/services/members.py) | Вторая дорога к заведению без владельца |

| Д-9 | Код — предъявительский токен, не привязан ни к какому `telegram_id` | [user.py:59](../src/db/models/user.py) | Кто первым набрал код, тот и стал этим человеком |
| Д-10 | Выданный код не виден и не отзывается после ухода с экрана выдачи | [access.py:620](../src/services/access.py) | Утёкший код невозможно погасить 7 дней |
| Д-11 | Перепривязать аккаунт невозможно | [staff.py:173](../src/bot/keyboards/staff.py) | Сменивший телеграм человек раздваивается, история делится пополам |

Про заявленное «на один аккаунт можно завести несколько человек»: **симптом реален, механика
обратная**. База двух сотрудников на одном `telegram_id` в одном заведении не допускает —
это запрещают `uq_users_telegram_id` и `uq_venue_members_user_venue`. Происходит худшее: два
реальных человека **схлопываются в одну строку**. Менеджер выдаёт код Ивану и код Марии, оба
активирует один аккаунт — в ростере остаётся один человек с именем Марии, ролью Марии и
должностью Марии, код Марии сожжён, а сама Мария в систему не попадёт никогда.

## 1.3 Целевая модель личности

Из неё выводятся все требования части I.

| Сущность | Ключ | Что несёт |
|---|---|---|
| Человек | `users.id` | вся история: `shifts.user_id`, `checklist_runs`, списания. Не переезжает никогда |
| Способ войти | `users.telegram_id` | ровно один на человека, уникален глобально |
| Сотрудник заведения | `venue_members.id` | роль, должность, `is_active` |
| Намерение нанять | `invite_codes.id` | ФИО текстом, роль, должность, срок. **Ещё не личность** |

**Т-1.1.** Требование заказчика «имена привязываются к айдишникам» реализуется так: ФИО
живёт на `users` рядом с `telegram_id`, и переписывать его вправе **только менеджер
осознанным действием** (`MemberService.rename`, решение B8). Ни одна автоматическая
операция ФИО не меняет.

**Т-1.2.** Главный инвариант, покрывающий Д-1, Д-7, Д-9:
**код приглашения может только дать доступ. Он никогда не понижает роль, не стирает
должность и не переписывает ФИО.**

## 1.4 Активация кода существующим участником

**Т-1.3.** `activate_invite_code` различает три состояния строки `venue_members`:

| Состояние | Поведение | Код |
|---|---|---|
| строки нет | как сейчас: создать с ролью и должностью с кода | сжигается |
| есть, `is_active = true` | **отказ** `InviteRejection.ALREADY_MEMBER` | **не сжигается** |
| есть, `is_active = false` (уволенный вернулся) | реактивация; роль = `max(текущая, с кода)` по рангу; должность = с кода или прежняя; **ФИО не трогается** | сжигается |

Третья строка — прямое следствие Т-1.2: вернувшийся управляющий не становится `staff`
оттого, что менеджер выписал ему `staff`-код.

**Почему отказ целиком, а не «принять только повышение».** Код не привязан ни к какому
`telegram_id` (Д-9). «Только повышение» оставляет дыру того же класса: сотрудник, которому
переслали код с ролью управляющего, повышает себя сам — и это уже не откатить, потому что
код сгорел. Требование «с одного аккаунта нельзя менять свой доступ» закрывается только
полным отказом. Канал смены роли остаётся ровно один — экран карточки (Т-1.8).

**Т-1.4.** Отказ наступает **на превью**, до подтверждения имени, а не после трёх экранов.
`preview_invite_code` получает `telegram_id` и возвращает `ALREADY_MEMBER`, если человек уже
активный участник заведения этого кода. Проверка на активации остаётся — гонка между
превью и нажатием возможна, это тот же приём, что уже применён для истёкшего кода.

**Т-1.5.** `_upsert_user` разделяется на два пути: человека нет — создать с ФИО из формы;
человек есть — обновляются **только** `username` и `is_active`, `full_name` не трогается
никогда. Закрывает Д-7.

**Т-1.6.** Флаг `was_already_member` получает читателя: экран возвращения отличается от
экрана вступления. Закрывает Д-8. Новые тексты в `src/bot/texts/onboarding.py`:

```
ONBOARDING_CODE_ALREADY_MEMBER  = "Вы уже в команде. Код не понадобился — роль меняет управляющий."
ONBOARDING_WELCOME_BACK_TEMPLATE = "С возвращением, {full_name}. Вы снова в команде «{venue}»."
```

## 1.5 Инвариант владельца

**Т-1.7.** В заведении всегда есть **хотя бы один активный владелец**. Проверяется в
сервисном слое одним методом `MemberService._assert_owner_remains`, который считает
владельцев *после* операции; ноль — отказ `LastOwnerError`.

Запрещаются: `set_role(последний owner → ниже)`, `deactivate(последний owner)`. Через
активацию кода состояние недостижимо по построению — это дополнительный аргумент за Т-1.3.

Подсчёт делается с `SELECT ... FOR UPDATE` по строкам владельцев: без блокировки два
параллельных понижения двух владельцев оба увидят «нас двое» и оставят ноль.

Текст: `STAFF_LAST_OWNER_REFUSED = "Это последний владелец. Сначала назначьте другого."`

Страховкой — constraint-триггер в БД (см. 1.10, п. 9). Он не UX, а последняя линия: если
сработал, значит сервис пропустил.

## 1.6 Операции над собой

**Т-1.8.** Актор не меняет собственную роль и не отключает сам себя. Правило записывается
один раз, в блоке гвардов `src/services/access.py`, рядом с остальными правами:

```python
def require_not_self(actor: AccessContext, member: VenueMember) -> None:
    if member.id == actor.member_id or member.user_id == actor.user_id:
        raise SelfTargetError(member.id)
```

Сравнение по обоим полям намеренно: `member_id` — быстрый путь, `user_id` — тот, который
переживёт пересборку карточки.

**Т-1.9.** Управляющий не распоряжается управляющим и владельцем:
`require_outranks_target` — если роль цели ≥ `manager`, требуется `owner`. Закрывает Д-5.

Встраивается в `set_role`, `deactivate`; `reactivate` получает только `require_outranks_target`.
Хендлеры не проверяют ничего — проверка на сервере, как требует ТЗ 9. Кнопка «Отключить» на
своей карточке при этом не рисуется, но серверный отказ остаётся вторым рубежом: скрытие
кнопки защитой не является.

Тексты: `STAFF_SELF_ROLE_REFUSED`, `STAFF_SELF_DEACTIVATE_REFUSED`, `STAFF_OWNER_ONLY_REFUSED`.

## 1.7 Право выдавать роли

**Т-1.10.** Правило «код с ролью выше `staff` выдаёт только владелец» сегодня реализовано
верно ([access.py:599](../src/services/access.py)), но **записано дважды** — второй раз в
клавиатуре (`issuable_roles`, чей докстринг сам это признаёт). Правило переносится в сервис,
клавиатура вызывает сервисный метод.

**[Открытый вопрос В-1]** Предлагается **запретить код с ролью `owner` вообще**, оставив
максимум `manager`. Владение выдаётся иначе: владелец открывает карточку **уже работающего**
сотрудника и меняет роль на `owner` с подтверждением. Обоснование: owner-код — это семь дней
живущий в мессенджере ключ от заведения, не привязанный ни к какому аккаунту. ТЗ 2 закрепляет
за владельцем «создание менеджеров» и про раздачу владения молчит, поэтому решение выносится
заказчику, а не принимается молча.

## 1.9 Перепривязка телеграма

**Т-1.13.** Карточка получает кнопку «Сменить телеграм». Менеджер выпускает код
`purpose='rebind'`, привязанный **к карточке**; новый аккаунт переходит по ссылке,
подтверждает, и меняется **только `users.telegram_id`**. Закрывает Д-11.

Ключевая мысль: меняется `telegram_id`, а **не** `venue_members.user_id`. Если двигать
`user_id`, вся история — смены, чек-листы, списания — останется висеть на старом человеке
и отчёты разъедутся. Меняя способ входа, историю не трогаем вообще.

Порядок проверок при активации: код валиден и имеет `purpose = rebind`; карточка существует
и активна; если `telegram_id` уже принадлежит **другому** человеку — отказ, код **не
сжигается** (менеджер должен разобраться, а не выпускать новый); если тому же — код гасится
без записи.

Старый телеграм после этого не имеет строки `users` и получает `ONBOARDING_NO_ACCESS` —
ровно то поведение, которое нужно при потерянном или уведённом аккаунте.

**Т-1.14.** `telegram_id` глобален, поэтому перепривязка меняет вход **во всех заведениях**,
где человек работает. Это говорится на экране до подтверждения:
`INVITE_REBIND_MULTI_VENUE_TEMPLATE = "Сотрудник работает ещё в {count} заведении — вход сменится везде."`

## 1.11 Миграция `0002_roles_and_binding`

1. Тип `bp_invite_purpose` (`join` | `rebind`), enum по образцу остальных.
2. `invite_codes.purpose` NOT NULL, `server_default='join'`.
3. `invite_codes.issued_to_member_id` BIGINT NULL, FK → `venue_members(id) ON DELETE CASCADE`.
4. `CHECK`: `(purpose='rebind') = (issued_to_member_id IS NOT NULL)`.
5. `CHECK`: `(used_at IS NULL) = (used_by IS NULL)`.
6. Частичный уникальный индекс: не более одного живого кода перепривязки на карточку.
7. Частичный индекс `(venue_id) WHERE role='owner' AND is_active` — под счёт владельцев.
8. Частичный индекс `(venue_id) WHERE used_at IS NULL AND revoked_at IS NULL` — под «Ждут активации».
9. Constraint-триггер последнего владельца, **`DEFERRABLE INITIALLY DEFERRED`**. Отложенность
   обязательна: передача владения «назначить нового, снять старого» — две операции в одной
   транзакции, немедленный триггер зарубил бы её на первой.

## 1.12 Приёмка части I

Этап принят, когда воспроизводятся следующие сценарии:

1. Владелец переходит по собственной ссылке с ролью управляющего → **роль не меняется**,
   код остаётся живым, на экране «Вы уже в команде».
2. Единственный владелец пытается понизить себя → отказ с объяснением.
3. Управляющий пытается отключить владельца → отказ.
4. Уволенный сотрудник активирует новый код → возвращается **со своей историей**, роль не
   понижается, ФИО не меняется.
5. Один аккаунт активирует два кода на разных людей → второй отклонён, оба человека целы.
6. Смена роли, должности и имени доступны из карточки; каждая операция в `audit_log`.
7. Сотрудник сменил телеграм → карточка перепривязана, история на месте, старый аккаунт
   доступа не имеет.
8. Выданные коды видны в разделе «Сотрудники» и отзываются оттуда.

**Каждый тест проверяется мутацией**: снять проверку — упасть должен именно этот тест.
Тесты этапа 0 показали, чего стоит тест, который не может упасть: восемь дефектов доступа
пережили 3102 зелёных теста, потому что ни один не проверял роль после повторной активации.

девять парсеров на пятнадцать листов. Общий контракт парсера — `Protocol`, результат разбора
— модель с построчным делением на «распознано / ошибка / предупреждение».

**Т-2.2.** Сервисный слой `src/services/import_service.py`: три режима, транзакционность,
откат. Бизнес-логика не живёт в парсерах, парсеры не знают про БД.

**Т-2.3.** `openpyxl` переносится из dev-зависимостей в runtime. Сейчас он в `[dev]`, а
образ собирается `pip install .` без него — прод упадёт на первом импорте, притом что тесты
останутся зелёными. Это тихий класс сбоя, ровно тот, против которого в проекте написаны
сторожа.

**Т-2.4.** Разбор книги выполняется через `asyncio.to_thread`. `openpyxl` синхронный, лист
на 1134 строки — это секунды блокировки event loop, то есть зависший бот для всего
заведения, а не медленный импорт.

## 2.2 Мастер в боте

**Т-2.5.** Новый раздел «Импорт» в «⚙️ Управление». Сценарий по ТЗ 7:

1. выбор типа данных → присылка файла;
2. **сопоставление колонок**: бот показывает, что нашёл («Колонка "Ингридиенты" → ингредиент.
   Верно?»), менеджер подтверждает или переназначает кнопками;
3. **превью**: «Найдено 142 строки, распознано 138, ошибок 4» + файл с построчным отчётом +
   первые 5 записей целиком;
4. «Импортировать» / «Отмена», импорт транзакционный — либо все валидные строки, либо ничего;
5. режимы «добавить» / «обновить по названию» / «заменить полностью», для последнего —
   отдельное подтверждение с числом удаляемых записей;
6. результат в `import_jobs`, изменения в `audit_log`, откат в течение суток.

**Т-2.6.** Схема сопоставления сохраняется на пару «заведение + тип данных» и при следующем
импорте того же файла мастер не задаёт вопросов. Для ежемесячного графика это решающая
деталь, а не удобство.

**Т-2.7.** Автоопределение колонок — по нормализованному тексту с допуском на опечатки.
В книге они реальны: `НАИМЕНОВНИЕ`, `Ингридиенты`, `Гаринр`. Последнее слово всегда за
человеком: структура файла у каждого заведения своя, и угадать её со стопроцентной
точностью нельзя.

**Т-2.8.** Отчёт об ошибках генерируется **в память** и отправляется как документ. Класть
его на диск нельзя: сторож поставки запрещает `.csv`/`.xlsx` внутри доставки.

## 2.3 Чего парсер обязан выдерживать

Из ТЗ 7 и разбора книги:

- заголовки ищутся **не только в первой строке**;
- строка-заголовок повторяется перед каждым рецептом и **сама является разделителем блоков**;
- пустые строки и строки-разделы не ломают разбор;
- количества приходят как `10.0`, `10`, `«топ»`, `«5 листиков»` — нечисловые сохраняются
  текстом в отдельное поле, а не выбрасываются;
- мусор из формул (`0`, `#REF!`) отбрасывается;
- **одна и та же книга читается по-разному в трёх состояниях**: в обезличенной копии ячейки
  с формулами читаются как `None`, в оригинале как `0`, в выгрузке из Google — как настоящие
  числа. Трактовка `None` как «пустая ячейка» молча теряет 27 дней месяца из листа графика.

## 2.5 Google Таблицы

## 3.2 Отчёт по смене

**Т-3.2.** Приоритет №1, оценка 6 человеко-дней. Книга из нескольких листов, где отдельным
листом идёт **«Не отмечено»** — то, что в смене пропустили.

**Т-3.3.** Формулировки пунктов читаются **через `run.template_id`**, а не через активный
шаблон. Иначе отчёт за прошлый месяц молча меняется после каждой правки чек-листа — прямое
нарушение ТЗ 4.3 и решения B3.

**Т-3.4.** Уволенный сотрудник обязан остаться в отчёте (ТЗ 5.1: деактивация сохраняет
историю). Наивное соединение по активным членам потеряет его, и отчёт за прошлый месяц
станет неполным задним числом.

**Т-3.5.** Код ложится в три места: `src/services/reports.py` (модель отчёта, ни одного
слова текста), `src/exporters/` (только формат, без домена), `src/bot/views/reports.py` +
`src/bot/texts/reports.py` (заголовки колонок — иначе падает сторож на кириллицу вне
`texts/`). Вызывает **хендлер**, а не планировщик: отчёт по расписанию — это уведомление,
а перечень уведомлений раздела 6 закрыт решением B9.

**Т-3.6.** Модель отчёта — снимок скаляров, а не строки SQLAlchemy: ленивый атрибут внутри
`asyncio.to_thread` обратится к async-сессии из чужого потока и сломается.

**Т-3.7.** Троттлинг обязан отличать выгрузку от нажатия. Сейчас квартальная выгрузка стоит
как сотни нажатий, а списывает один токен; двадцать подряд кладут процесс.

# Часть IV. Автодополнение при вводе

## 4.1 Два разных механизма

Заказчик описал одним словом две вещи, которые в телеграме реализуются несовместимо. Это
надо развести до начала работ.

**(а) Инлайн-режим.** Человек набирает `@имя_бота мохи` в любом чате, и над клавиатурой
всплывает список. Это **настоящее** автодополнение по мере ввода, и телеграм умеет только
такое. Технически возможно, инфраструктура почти готова.

**(б) «Список обновляется, пока пишу боту в диалоге».** **Физически невозможно.** Телеграм
не присылает событий, пока человек не нажал «Отправить»; бот не видит набора по буквам.
Честная замена — кнопка `switch_inline_query_current_chat`, которая запускает механизм (а)
прямо в чате с ботом: человек нажимает кнопку, в поле ввода подставляется `@бот `, и дальше
список работает по-настоящему.

## 4.2 Требования

**Т-4.1.** Включается инлайн-режим: `/setinline` у @BotFather, регистрация обработчика,
роутер в дереве. Если обработчик зарегистрирован, но роутер не попал в дерево, телеграм не
станет слать события вовсе, а симптом неотличим от невключённого режима у BotFather.

**Т-4.2. Критично для безопасности.** Ответ на инлайн-запрос обязан ставить
**`is_personal=True`**. Без этого телеграм кэширует выдачу по строке запроса **для всех
пользователей сразу**: бармен заведения Б наберёт «мохито» и получит рецептуру заведения А,
не коснувшись нашей базы. Это утечка между заведениями мимо всех репозиторных предикатов и
прямое нарушение критерия приёмки 11.3. Обычный тест «чужое заведение не видно» её не
поймает — нужен тест на аргументы вызова.

**Т-4.3.** Ветки отказа обязаны уметь отвечать на инлайн-запрос. Сегодня middleware
авторизации и venue-контекста обрабатывают только сообщения и нажатия; уволенный сотрудник
получит молчание, а на клиенте это бесконечная загрузка без объяснения.

**Т-4.4.** Бюджет троттлинга для инлайна выделяется отдельно. Сейчас инлайн попадает в
бюджет команд — одна в секунду; набор из шести букв исчерпает его на пятой, список замрёт
посреди слова. Это ровно тот сценарий «бармен читает это как сломанный бот», ради которого
бюджеты уже разделяли.

**Т-4.5.** `cache_time = 0`. Любое другое значение — окно, в котором не выполняется прямое
обещание ТЗ 5.5: «изменённая рецептура немедленно доступна всем сотрудникам».

## 4.3 Где это нужнее, чем в рецептах

**Т-4.6.** Поиск по рецептам **уже написан** (`RecipeService.search`, с `pg_trgm`), и инлайн
над ним — самая дешёвая часть. А инфраструктуры поиска по номенклатуре — для списания и
заказа — **не существует вовсе**, притом что ТЗ 5.6 требует поиска по названию именно там,
и именно там ввод идёт под давлением смены.

**[Открытый вопрос В-4]** Что делать раньше: рецепты (как просил заказчик) или номенклатуру
под списание. Рецепты дешевле, списание полезнее.

**Т-4.7.** Подбор сотрудника по имени (выбор на смену) идёт **только** через
`VenueMemberRepo`. Таблица `users` глобальная: поиск напрямую по ней вернёт персонал всех
заведений. Нужен тест изоляции, проверенный мутацией.

# 7. Отдельно: найдено на живом стенде

**Т-7.1.** Заполнение шаблона чек-листа после того, как по смене уже ушло уведомление
«шаблон не заполнен», **не приводит к отправке чек-листа**: строка в очереди помечена
доставленной, и дедупликация справедливо не даёт отправить второй раз.

Наблюдалось вживую: в 10:06 ушло «в шаблоне нет ни одного пункта», в 10:07 менеджер
заполнил шаблон двумя пунктами, смена начиналась в 13:07 — чек-лист так и не пришёл.
Формально всё верно, по ощущению — «бот не работает».

Требование: если шаблон заполнен, а смена, по которой ушло уведомление о пустом шаблоне,
**ещё не началась**, чек-лист ставится в очередь заново.
