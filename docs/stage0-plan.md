## Объём

**Входит:** онбординг и коды приглашения · главное меню · создание заведения через
интерфейс · ручное создание смены · чек-лист открытия (группы, отметки, завершение
с пропусками) · минимальный редактор чек-листа, сотрудников и рецептов · карточка рецепта
с поиском · **одно запланированное уведомление** (чек-лист открытия) **плюс три событийных
уведомления менеджеру** (завершение с пропусками, пустой шаблон, «рецепта нет») ·
пустые состояния во всех разделах.

**Не входит (этап 1):** импорт Excel и мастер сопоставления · чек-лист закрытия и `stock` ·
фото в пунктах · эскалация критичных пунктов · списание · заказ · база знаний · отчёты ·
групповой чат `/bind` · inline-режим · заготовки отдельным разделом · замена смены с
переездом уведомлений · «График всей команды» · «Показать весь месяц» · переключение
активного заведения · остальные типы уведомлений раздела 6.

**Требование ко всем экранам (ТЗ 8.1):** экран без спроектированного пустого состояния
не считается сделанным. Отдельной задачи «пустые состояния» в конце плана нет намеренно.

## Технические решения (ТЗ 0 п.2)

| ID | Решение | Обоснование |
|---|---|---|
| D1 | `checklist_type ENUM('opening','closing','stock')` — единый именованный PG-тип для `checklist_templates` и `checklist_runs` | В 4.3 два значения, в 5.4 и выводе 1.6 — три |
| D2 | Группировка пунктов — плоскими полями `group_name`, `group_index`, сортировка `(group_index, order_index)`. Группа не существует без пунктов | 5.4 требует эти поля буквально |
| D3 | Первый владелец — по ответу на A3. При любом варианте после создания заведения появляется полноценная строка `venue_members(owner)`: права читаются только из БД, как требует ТЗ 2 | Env — одноразовый триггер, не источник прав |
| D4 | `qty_text TEXT NULL` в `recipe_ingredients`; `qty` и `unit` **оба** nullable | 5.5 показывает «Содовая — топ»; раздел 7 требует хранить нечисловые количества текстом. В референсе есть и количество без единицы (`45.0`), и единица внутри текста (`топ ( 100 мл )`, `5 листиков`, `2/3 деш`) |
| D5 | `notifications`: `entity`/`entity_id`, `dedup_key`, `attempts`, `chat_id`, статус `sending`. Единственная очередь — таблица; персистентный jobstore APScheduler не используем | Два источника истины расходятся; без `dedup_key` критерий 11.4 непроверяем |
| D6 | Уникальность рецепта — `(venue_id, category, lower(btrim(name)))`, тем же ключом определяется перекрытие глобальной записи локальной | Проверено по референсу: `Americano` встречается дважды (коктейль и кофе), `Ягодный` дважды. Ключ по одному названию отверг бы реальные данные заведения |
| D7 | Один активный шаблон на пару (venue, type) — partial unique index `WHERE is_active` | Иначе «текущий шаблон» нельзя найти надёжно |
| D8 | Инвариант «ровно один opener/closer на дату» — в сервисном слое, не жёстким индексом | Жёсткий индекс не даст пройти транзакции сценария замены на этапе 1 |
| D9 | Мультитенантность: ровно две формы запроса в базовом репозитории — `for_venue` и `library` (белый список: `recipes`, `knowledge_articles`). Дочерние строки адресуются только через join к родителю | Снимает противоречие 3.3 и 11.3. `preps` в белый список не включаем до ответа на C4 |
| D10 | Правило «максимум 2 уровня вложенности» (5.2) относится к навигации до входа в сценарий; шаги FSM вложенностью не считаются | Иначе собственные сценарии ТЗ (списание — 6 шагов) нарушают его же правило |
| D11 | Чек-лист рисуется **текстом сообщения**, кнопками — компактные маркеры пунктов текущей группы | 40 inline-кнопок с текстами вроде «Наличие гостевых салфеток» не влезают ни в лимит 20 символов (8.2), ни в экран |
| D12 | Все `TIME`-поля — локальное время заведения, все `timestamptz` — UTC, конверсия в одном модуле `src/services/timezones.py`; ни один хендлер не вызывает `datetime.now()`. Несуществующее локальное время сдвигается вперёд, неоднозначное берётся с `fold=0` | 3.4 + критерий 11.2 |
| D13 | Скрипт заливки фрагмента — в `tests/tools/`, падает при `APP_ENV=prod`, факт неимпорта закрыт статическим тестом 35 | Раздел 12 разрешает фикстуры только внутри `tests/`; дисциплина словами не держится |
| D14 | PK — `BIGINT GENERATED BY DEFAULT AS IDENTITY`, не UUID. Схема префиксов `callback_data` — в одном модуле, бюджет 64 байта | Два UUID в кнопке чек-листа (`run_id` + `item_id`) — 72 байта, кнопки просто не соберутся. Защита от чужих id обеспечивается серверной проверкой принадлежности заведению (ТЗ 9), а не неугадываемостью |
